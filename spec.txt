# tpt-proto20 Design Document

**Project name:** tpt-proto20  
**Document status:** Full-scope design  
**Implementation model:** Clean-room  
**Primary language:** Rust  
**License:** MIT OR Apache-2.0  
**Compatibility strategy:** Native next-generation design with official adapters for Protocol Buffers and gRPC compatibility

---

## 1. Summary

`tpt-proto20` is a next-generation, schema-first contract system for distributed applications.

It combines:

- a modern schema language
- a pure-Rust compiler
- a compact binary wire format
- a Rust-first runtime
- generated code
- reflection
- JSON/text representations
- schema evolution tooling
- security-hardened decoding
- observability
- an RPC/streaming system
- compatibility adapters for existing Protocol Buffers and gRPC ecosystems

The goal is not merely to serialize data.

The goal is to allow independently evolving programs to communicate safely, efficiently, and predictably over time.

---

## 2. Vision

`tpt-proto20` should be the contract layer for distributed systems.

It should answer these questions:

- What data is being sent?
- What version of the contract is in use?
- Is this change safe?
- Can old clients read new messages?
- Can new clients tolerate old messages?
- Can untrusted input be decoded safely?
- Can messages be inspected, debugged, and converted?
- Can services stream, cancel, timeout, and observe requests cleanly?
- Can Rust developers use the system without fighting the toolchain?
- Can other languages interoperate with the system?

The project should feel like a complete contract toolchain, not just a codec.

---

## 3. Design principles

### 3.1 Schema-first

Every message, enum, and service is defined by a schema.

The schema is the source of truth.

### 3.2 Explicit evolution

Schema changes must be explicit, analyzable, and classified.

The compiler should detect:

- safe additions
- risky renames
- breaking removals
- field ID reuse
- type changes
- service contract changes

### 3.3 Safe by default

Decoding untrusted input must be safe.

Default decoder limits must protect against:

- excessive allocation
- deep recursion
- huge messages
- excessive field counts
- oversized strings
- oversized byte fields
- malicious repeated fields
- malicious map fields

### 3.4 Rust-first, but polyglot

The reference implementation is Rust.

The system should also support other languages through:

- a neutral compiler IR
- descriptor outputs
- language-specific code generators
- language-specific runtimes

### 3.5 Zero-copy friendly

The runtime should support:

- owned messages
- borrowed views
- bytes-backed messages
- dynamic messages

Zero-copy should be a first-class design consideration.

### 3.6 Observability built in

RPC and message tooling should provide:

- metrics
- tracing
- structured errors
- debugging tools
- schema-aware inspection

### 3.7 Compatibility through adapters

`tpt-proto20` should support migration from existing protobuf/gRPC systems through compatibility layers.

The project should allow:

```text
existing protobuf/gRPC system
  -> adapter
    -> gradual migration
      -> native tpt20 usage
```

### 3.8 Tooling is part of the protocol

A protocol without tooling is incomplete.

`tpt-proto20` includes:

- formatter
- linter
- diff tool
- code generator
- conformance suite
- CLI debugger
- schema registry support

## 6. Schema language

`tpt-proto20` uses a modern schema language with the file extension:

```text
.tpt
```

The language should be concise, explicit, and easy to lint.

### 6.1 Example schema

```tpt
package user.v1;

message User {
  1: id int64;
  2: name string;
  3: email string?;
  4: roles repeated Role;
  5: created_at Timestamp;
}

enum Role {
  UNKNOWN = 0;
  ADMIN = 1;
  MEMBER = 2;
  AUDITOR = 3;
}

message GetUserRequest {
  1: user_id int64;
}

message WatchUsersRequest {
  1: include_deleted bool;
}

service UserService {
  get_user(GetUserRequest) -> User;
  watch_users(WatchUsersRequest) -> stream User;
}
```

### 6.2 Field IDs

Every field must have a stable numeric ID.

```tpt
1: id int64;
```

Field IDs are part of the wire contract.

Once a schema is published, field IDs must not be reused.

### 6.3 Presence

Optional presence is explicit.

Implicit presence:

```tpt
1: age int32;
```

Explicit presence:

```tpt
1: age int32?;
```

Rules:

- implicit presence means absence equals default
- explicit presence means absence is distinguishable from default
- message fields are presence-aware
- required fields are not part of the language

### 6.4 Repeated fields

```tpt
1: tags repeated string;
```

Repeated fields are lists.

### 6.5 Maps

```tpt
1: labels map<string, string>;
```

Maps must have:

- scalar or string key types
- valid value types
- deterministic encoding rules
- runtime size limits

### 6.6 Oneofs

```tpt
message Contact {
  oneof method {
    1: email string;
    2: phone string;
    3: device_token string;
  }
}
```

Oneofs represent mutually exclusive fields.

### 6.7 Enums

```tpt
enum Status {
  UNKNOWN = 0;
  ACTIVE = 1;
  SUSPENDED = 2;
}
```

Rules:

- enum values have stable numeric IDs
- aliases may be supported with explicit annotation
- unknown enum handling must be defined by enum openness
- closed enums reject unknown values
- open enums preserve unknown values

### 6.8 Services

```tpt
service UserService {
  get_user(GetUserRequest) -> User;
  watch_users(WatchUsersRequest) -> stream User;
  upload_logs(stream LogEntry) -> UploadSummary;
  chat(stream ChatMessage) -> stream ChatMessage;
}
```

Service methods support:

- unary
- server streaming
- client streaming
- bidirectional streaming

### 6.9 Annotations

Annotations extend schema metadata.

Example:

```tpt
message CreateUserRequest {
  1: email string? @max_len(254);
  2: age int32? @range(min: 0, max: 150);
  3: username string @pattern("^[a-z0-9_]{3,32}$");
}
```

Annotations may be used for:

- validation hints
- documentation
- codegen options
- compatibility policies
- observability metadata
- auth rules
- storage hints

Core annotations are standardized. Custom annotations are allowed through a registry.

## 7. Compiler

The `tpt20` compiler transforms schema files into machine-usable artifacts.

### 7.1 Compiler pipeline

```text
.tpt files
  -> lexer
  -> parser
  -> AST
  -> semantic analysis
  -> compatibility checks
  -> IR generation
  -> descriptor generation
  -> code generation
```

### 7.2 Compiler outputs

The compiler produces:

```text
IR
descriptor set
schema fingerprint
generated code
diagnostics
compatibility report
```

### 7.3 Diagnostics

Diagnostics must include:

- file path
- line number
- column number
- span
- severity
- error code
- human-readable explanation
- suggested fix where possible

Example:

```text
error[E0042]: field ID 3 was removed without reservation
  --> schema/user.v1.tpt:12:3
  |
  = help: reserve field ID 3 to preserve compatibility
```

### 7.4 Schema fingerprint

Every compiled schema must produce a stable fingerprint.

The fingerprint is derived from the canonical descriptor.

Uses:

- schema registries
- dynamic message validation
- debugging
- migration tooling
- compatibility auditing

## 9. Native binary wire format

`tpt-proto20` defines its own native binary wire format.

The format must be:

- compact
- deterministic when requested
- safe to decode
- zero-copy friendly
- easy to skip
- forward-compatible
- backward-compatible where possible

### 9.1 Wire classes

| Wire class | Meaning |
|---:|---|
| 0 | VARINT |
| 1 | FIXED32 |
| 2 | FIXED64 |
| 3 | LEN |

`LEN` is used for:

- bytes
- strings
- nested messages
- packed repeated fields
- map entries

### 9.2 Tag encoding

Each field begins with a tag:

```text
tag = (field_id << 3) | wire_class
```

The tag is encoded as a varint.

### 9.3 Scalar types

The following scalar types must be supported:

```text
bool
int32
int64
uint32
uint64
sint32
sint64
fixed32
fixed64
sfixed32
sfixed64
float32
float64
string
bytes
```

### 9.4 Varints

Varints encode unsigned integers using 7-bit groups.

Signed integers use zigzag encoding where appropriate.

The decoder must reject:

- truncated varints
- overlong varints
- overflowing varints
- malformed payloads

### 9.5 Length-delimited fields

Length-delimited fields are encoded as:

```text
length as varint
payload bytes
```

The decoder must reject:

- negative lengths
- overflowing lengths
- truncated payloads
- invalid UTF-8 for strings
- payloads exceeding limits

### 9.6 Repeated fields

Repeated fields support:

- unpacked encoding
- packed encoding
- mixed input encoding

Decoders must accept both packed and unpacked forms for compatible scalar repeated fields.

### 9.7 Maps

Maps are encoded as repeated synthetic map-entry messages.

Map entry fields:

```text
key = field 1
value = field 2
```

Rules:

- duplicate map entries must be accepted
- later values override earlier values by default
- deterministic encoding must sort map entries consistently
- map entries must respect decoder limits

### 9.8 Oneofs

Oneof fields are encoded as normal fields.

Decoding rules:

- if multiple fields in the same oneof appear, the last one wins
- generated APIs expose the oneof as a mutually exclusive type

### 9.9 Unknown fields

Unknown fields must be preserved by default.

Unknown field policies:

```text
preserve
discard
fail
```

Preserved unknown fields must be re-encodable.

### 9.10 Canonical encoding

The system must support canonical deterministic encoding.

Canonical mode must define:

- field order
- map ordering
- unknown field ordering
- canonical varint representation
- repeated field ordering where applicable
- oneof serialization behavior

Canonical encoding is useful for:

- hashing
- signatures
- auditing
- reproducible builds
- content addressing

### 9.11 Optional envelope

For storage, event systems, and dynamic registries, messages may be wrapped in an envelope.

```tpt
message Envelope {
  1: schema_id bytes;
  2: schema_version string;
  3: payload bytes;
}
```

The envelope is optional.

It is not required for normal RPC payloads.

## 10. Compatibility adapters

`tpt-proto20` must provide compatibility with the existing protobuf/gRPC ecosystem.

### 10.1 Protobuf schema import

The compiler should import `.proto` files.

Example:

```sh
tpt20 import user.proto --out user.tpt
```

Import support includes:

- proto2
- proto3
- editions where feasible
- messages
- enums
- oneofs
- maps
- services
- options where meaningful
- reserved fields
- extensions where feasible

### 10.2 Protobuf wire adapter

The runtime should support encoding and decoding protobuf-compatible binary messages.

Conceptual API:

```rust
let user = User::decode_protobuf(bytes)?;
let bytes = user.encode_protobuf();
```

This allows gradual migration.

### 10.3 gRPC bridge

The RPC layer should support compatibility with gRPC.

This includes:

- HTTP/2 framing compatible with gRPC
- protobuf-compatible message payloads
- status mapping
- metadata mapping
- deadline mapping
- streaming modes
- health checking
- reflection where feasible

This allows `tpt-proto20` services to communicate with existing gRPC systems during migration.

## 11. Runtime message model

The Rust runtime must support multiple message representations.

### 11.1 Owned messages

Owned messages own all data.

```rust
pub struct User {
    pub id: i64,
    pub name: String,
    pub email: Option<String>,
}
```

### 11.2 Borrowed messages

Borrowed messages avoid allocation where possible.

```rust
pub struct UserView<'a> {
    pub id: i64,
    pub name: &'a str,
    pub email: Option<&'a str>,
}
```

### 11.3 Bytes-backed messages

Bytes-backed messages allow efficient slicing and sharing.

They are useful for:

- proxies
- caches
- streaming pipelines
- zero-copy gateways

### 11.4 Dynamic messages

Dynamic messages are descriptor-driven.

They require no compile-time generated types.

```rust
let message = DynamicMessage::decode(descriptor, bytes)?;
```

Dynamic messages support:

- field lookup
- field mutation
- unknown fields
- reflection
- JSON conversion
- text conversion

## 12. Code generation

The Rust code generator must produce idiomatic, safe, maintainable code.

### 12.1 Generated message types

For:

```tpt
message User {
  1: id int64;
  2: name string;
  3: email string?;
}
```

The generator may produce:

```rust
pub struct User {
    pub id: i64,
    pub name: String,
    pub email: Option<String>,
}
```

### 12.2 Generated methods

Generated messages should provide:

```rust
impl User {
    pub fn encode(&self) -> Vec<u8>;
    pub fn decode(bytes: &[u8]) -> Result<Self, DecodeError>;
    pub fn decode_borrowed(bytes: &[u8]) -> Result<UserView<'_>, DecodeError>;
    pub fn to_json(&self) -> Result<String, JsonError>;
    pub fn from_json(json: &str) -> Result<Self, JsonError>;
}
```

### 12.3 Builders

Builders should be generated where enabled.

```rust
let user = User::builder()
    .id(42)
    .name("Ada")
    .email("ada@example.com")
    .build()?;
```

Builders may validate:

- presence requirements
- oneof constraints
- annotation constraints
- enum validity
- map key validity

### 12.4 Generated enums

Enums should be represented as Rust enums with integer conversion support.

Unknown enum handling must respect open/closed semantics.

### 12.5 Generated oneofs

Oneofs should be represented as Rust enums.

```rust
pub enum ContactMethod {
    Email(String),
    Phone(String),
    DeviceToken(String),
}
```

### 12.6 Generated services

Service code generation should produce:

- server traits
- client stubs
- streaming interfaces
- metadata helpers
- deadline helpers
- cancellation helpers

Example:

```rust
#[async_trait]
pub trait UserService {
    async fn get_user(
        &self,
        ctx: RpcContext,
        request: GetUserRequest,
    ) -> Result<Response<User>, RpcError>;
}
```

## 16. RPC system

`tpt-proto20` includes an RPC system.

The RPC system must support:

- unary calls
- server streaming
- client streaming
- bidirectional streaming
- deadlines
- cancellation
- metadata
- status codes
- rich error details
- compression
- authentication
- authorization
- retries
- backpressure
- observability

### 16.1 RPC context

Every RPC should carry a context.

```rust
pub struct RpcContext {
    pub deadline: Deadline,
    pub cancellation: CancellationToken,
    pub metadata: Metadata,
    pub trace: TraceContext,
    pub peer: Option<PeerInfo>,
    pub extensions: Extensions,
}
```

Handlers should be able to inspect:

```rust
ctx.is_expired()
ctx.remaining_time()
ctx.metadata()
ctx.trace()
```

### 16.2 Streaming APIs

Streaming APIs should be backpressure-aware.

Server streaming example:

```rust
async fn watch_users(
    &self,
    ctx: RpcContext,
    request: WatchUsersRequest,
    sink: ServerStreamSink<User>,
) -> Result<(), RpcError>;
```

Client streaming example:

```rust
async fn upload_logs(
    &self,
    ctx: RpcContext,
    input: ClientStreamSource<LogEntry>,
) -> Result<Response<UploadSummary>, RpcError>;
```

Bidirectional streaming example:

```rust
async fn chat(
    &self,
    ctx: RpcContext,
    stream: BidiStream<ChatMessage>,
) -> Result<(), RpcError>;
```

### 16.3 Status codes

The RPC system must define standard status codes.

Required codes:

```text
OK
CANCELLED
UNKNOWN
INVALID_ARGUMENT
DEADLINE_EXCEEDED
NOT_FOUND
ALREADY_EXISTS
PERMISSION_DENIED
RESOURCE_EXHAUSTED
FAILED_PRECONDITION
ABORTED
OUT_OF_RANGE
UNIMPLEMENTED
INTERNAL
UNAVAILABLE
DATA_LOSS
UNAUTHENTICATED
```

### 16.4 Rich errors

Errors should support structured details.

Example:

```rust
let error = RpcError::invalid_argument("validation failed")
    .with_details(ValidationFailure {
        field: "email".to_string(),
        reason: "invalid format".to_string(),
    })?;
```

Rich error details should be compatible with descriptor-based dynamic decoding.

### 16.5 Metadata

Metadata is carried alongside RPC calls.

Rules:

- metadata keys should be lowercase
- binary metadata should use a standard suffix convention
- metadata size limits must be enforced
- reserved metadata keys must be protected

## 17. Transport layer

The RPC system should be transport-agnostic.

Supported transports:

```text
HTTP/2
in-process
QUIC/HTTP3 optional
custom stream transports optional
```

The required production transport is HTTP/2 because of ecosystem compatibility.

### 17.1 HTTP/2 requirements

The HTTP/2 transport must support:

- multiplexed streams
- trailers
- flow control
- stream reset
- GOAWAY handling
- keepalive/ping behavior
- TLS with ALPN
- cleartext h2c for local development when explicitly enabled

### 17.2 Message framing

RPC messages must be framed.

Conceptual frame:

```text
1 byte flags
4 bytes big-endian length
N bytes payload
```

Flags may indicate:

- compression enabled
- future protocol extensions

### 17.3 In-process transport

The system must provide an in-process transport for:

- tests
- embedded systems
- local development
- benchmarking
- fuzzing

## 18. Security model

`tpt-proto20` must assume hostile input.

### 18.1 Decoder limits

The runtime must enforce limits.

```rust
pub struct DecoderLimits {
    pub max_message_bytes: usize,
    pub max_depth: u32,
    pub max_field_count: usize,
    pub max_unknown_field_bytes: usize,
    pub max_string_bytes: usize,
    pub max_bytes_field_bytes: usize,
    pub max_repeated_entries: usize,
    pub max_map_entries: usize,
}
```

### 18.2 Integer safety

Integer operations must use checked arithmetic where overflow is possible.

### 18.3 UTF-8 validation

String fields must be validated.

### 18.4 Recursion control

Nested message depth must be bounded.

### 18.5 Allocation control

Allocations must be bounded and predictable.

### 18.6 RPC security

The RPC layer must support:

- TLS
- mTLS
- token authentication
- metadata authentication
- authorization middleware
- peer inspection
- rate limiting hooks
- request limits
- deadline enforcement

### 18.7 Unsafe policy

Default policy:

```text
no unsafe in core decoding paths
```

Unsafe may only be used when:

- isolated
- documented
- tested
- feature-gated
- justified by measurable benefit

## 20. Schema evolution and governance

`tpt-proto20` must make schema evolution safe.

### 20.1 Compatibility classes

Changes are classified as:

```text
SAFE
WARNING
BREAKING
```

### 20.2 Safe changes

Examples:

- add optional field
- add repeated field
- add new enum value in open enums
- add new service method
- reserve removed field IDs

### 20.3 Warning changes

Examples:

- rename field but keep ID
- rename method
- change documentation semantics
- change annotation behavior

### 20.4 Breaking changes

Examples:

- change field type
- change field ID
- remove field without reservation
- remove service method without compatibility policy
- change streaming direction
- change request type incompatibly
- change response type incompatibly

### 20.5 Schema history

The toolchain should support schema history manifests.

A manifest can record:

- schema versions
- fingerprints
- compatibility policies
- migration notes
- reserved IDs
- deprecation dates

## 29. Glossary

### Schema

A declarative definition of messages, enums, and services.

### Descriptor

A machine-readable representation of a compiled schema.

### IR

Intermediate representation used by the compiler to support multiple language backends.

### Wire format

The binary encoding used to serialize messages.

### Reflection

Runtime access to schema structure and dynamic messages.

### RPC

Remote Procedure Call.

### Streaming

A call pattern where multiple messages are sent or received.

### Deadline

A point in time after which an RPC should be considered expired.

### Cancellation

A signal that an operation should stop.

### Compatibility adapter

A layer that allows `tpt-proto20` to interoperate with existing protobuf/gRPC systems.

### Schema fingerprint

A stable hash representing a compiled schema.

### Canonical encoding

A deterministic encoding mode suitable for hashing and signing.
